# Release-candidate checklist (pre-1.0)

A release candidate is for **outside testing**, not itself a 1.0 release. Use the [outside-tester plan](outside-tester-plan.md) for regressions and redacted results. The [clean-machine verification record](clean-machine-verification.md#user-reported-phase-5-acceptance-2026-11-04) includes the user's explicit Phase 5 acceptance for the local 0.9.0-rc.1 build. That acceptance does not verify a later 1.0.0 binary or replace CI, checksum, provenance, or public-release checks.

> **1.0.0 status (2026-11-05):** 1.0.0 was published after the owner accepted the CI-verified artifacts without a second-machine rerun. This checklist remains for future release candidates; see the [1.0 release record](release-1.0-checklist.md) for what was completed and waived.

## Prepare the candidate

- [ ] Identify the exact pre-1.0 version, source commit, and build/run used for the candidate. Keep the candidate artifacts together with their checksum file; do not mix artifacts from different runs.
- [ ] Check the Windows CI run for that commit/tag: the `verify` job must pass its install, tests, build, synthetic built-renderer smoke (not an installer test), lint, workflow/tooling format check, audit, and secret-history scan; the `windows-release` job (on a version-matched `v*` tag after the recorded Phase 5 acceptance) must finish packaging exactly one version-matched NSIS and one portable EXE, writing `SHA256SUMS.txt`, creating build-provenance attestations for the EXEs, and uploading the artifacts. A local `npm run dist:win` build does **not** acquire the workflow's attestations.
- [ ] Disclose to testers that the Windows EXEs are **unsigned**. SignPath/code signing is **not configured**; Windows SmartScreen may warn. Do not describe checksums or GitHub provenance as an Authenticode signature or tell testers to ignore a warning without verifying the source and artifact.
- [ ] Test keyboard navigation, visible focus, review/restore dialog focus and Escape behavior, and readability/contrast at Windows display scaling and high-contrast settings. Record any remaining accessibility blockers; a synthetic browser preview alone cannot certify the packaged app.
- [ ] Review the [code-signing readiness notes](code-signing-readiness.md) and current SignPath Foundation eligibility/terms with the user before applying. Signing requires account ownership and protected credentials; no application, signing integration, or Authenticode verification is configured yet.
- [ ] Provide the candidate only to willing outside testers with their own licensed games and compatible engines. Explain that the app does not bundle games, engines, or Bot Warfare; the latter is installed only on request. Give them the [clean-machine checklist](clean-machine-verification.md) and a private way to report sensitive issues (see [SECURITY.md](../SECURITY.md)). Do not request private launchers, keys, configs, command lines, raw logs, or unredacted screenshots.

## Verify downloads before running them

These instructions apply to the **tagged CI artifact**, not an arbitrary locally built EXE. Obtain the installer/portable EXEs and `SHA256SUMS.txt` from the same successful `windows-release` GitHub Actions run for the expected repository and source tag/commit. The workflow uploads these as an Actions artifact; it does not publish a GitHub Release. Downloading a similarly named file from elsewhere is not equivalent.

1. Extract the artifact and inspect `SHA256SUMS.txt`. In PowerShell, for **each** `.exe` listed, calculate its hash with `Get-FileHash -Algorithm SHA256 -LiteralPath '.\<exact-file-name>.exe'` and compare it to the 64-character hex digest on that file's line (case-insensitive). Reject missing files or mismatches. A checksum file downloaded alongside a malicious binary can itself be replaced; this comparison checks consistency, not who built it.
2. With a current [GitHub CLI](https://cli.github.com/) authenticated to access the repository's attestations, run `gh attestation verify '.\<exact-file-name>.exe' --repo OWNER/REPO` for **each** EXE, replacing `OWNER/REPO` with the expected repository. Confirm successful verification and inspect the reported source repository, source commit/tag, and GitHub Actions workflow against the intended CI run. Reject a failed/missing attestation or an unexpected source. The attestation covers the EXEs, not `SHA256SUMS.txt` or the artifact ZIP.
3. Only after both checks agree with the intended source should a tester decide whether to run the **unsigned** build. Provenance identifies the build origin; it does not code-sign the executable or prove the application is safe. If no tagged CI artifact/attestation exists, say so and do not claim provenance verification for a local build.

## Outside-test and acceptance gate

- [x] The user reported a separate-PC/VM install/portable journey, client connections and visible in-game bots for all six titles on the local 0.9.0-rc.1 build, along with guided edit/backup, Stop/port-release and real firewall/UAC checks. The user explicitly accepted Phase 5; see the [record](clean-machine-verification.md#user-reported-phase-5-acceptance-2026-11-04). This is a user attestation, not independently inspected test artifacts.
- [ ] If the 1.0.0 build differs in installation, launch, configuration or networking behavior, rerun affected per-title journeys on a separate Windows PC/VM and record redacted outcomes. A bound UDP port alone is not a bot-join pass.
- [ ] Before publishing, verify the exact final installer and portable bytes, their matching checksums and provenance, and obtain the owner's release approval. Phase 5 acceptance alone does not publish or attest 1.0.0.
